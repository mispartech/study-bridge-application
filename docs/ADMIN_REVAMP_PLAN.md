# StudyBridge — Admin revamp: phased implementation plan

Save as `docs/ADMIN_REVAMP_PLAN.md`. Companion to `docs/ADMIN_REVAMP_BRIEF.md` (the snapshot of 22 Nov 2026).
**The codebase is the source of truth.** Before each phase, check the brief's claims against the code, and stop to report any difference that changes the plan.

How to use this file: run **one phase at a time**. Each phase ends with a prompt to send to Claude Code. A phase is done only when every acceptance criterion passes, all tests are green, and it is merged to `main`.

## 0. Rules for every phase

These come from `CLAUDE.md`, `docs/SPEC_ACCESS_ADMIN.md` and the brief, and bind every phase.

**Data rules (also for every new record type)**
- Facts come only from the database: never hard-coded, never generated by AI at read time.
- Every content record carries `source_url`, `last_verified_at` and `confidence`, and the admin shows freshness.
- New content reaches students only through the review queue, approved by a `data_editor` or `admin`.
- Links to apply, funding or licensing pages must be on an allow-listed official domain.
- Money is stored in integer minor units with a currency code, and shown in NGN first.
- Visa and nationality rules stay hard filters in matching.

**Access rules**
- Permissions are defined once in `lib/admin/permissions.ts` (or the existing equivalent). Navigation, pages, server actions and API routes all read from it.
- Every admin page and every admin API checks its permission **on the server**. Hiding a link is never the check.
- Staff need TOTP at assurance level aal2, and sessions expire after 8 hours idle. New routes inherit this from the admin layout, and a test proves it.
- Every staff mutation writes to `staff_audit` (append-only), with before/after values where relevant. Bulk actions write **one audit row per record**, plus one row for the bulk action itself.
- `activity_event` properties never contain personal data or free text. New events need a Zod schema.
- Advisor message text is never shown in the admin, except where `SPEC_ACCESS_ADMIN.md` already allows it (flagged items, with a logged reason).

**Engineering rules**
- Admin code stays out of the student bundle. The 360px / slow-3G budgets for student pages must not regress (Playwright checks stay green).
- Dates and periods use Lagos days (Africa/Lagos), the same as today.
- Each phase adds Vitest units for logic and Playwright for flows, on desktop and the 360px phone profile.
- Each phase updates `docs/` (this file's status line, plus any new spec) and `CLAUDE.md` if conventions change.
- Migrations are tested on the development Supabase project first, never applied first to production.

**Permission matrix (current, plus the additions this plan proposes)**

| Permission | support | data_editor | admin | Added in |
|---|---|---|---|---|
| overview | ✓ | – | ✓ | existing |
| users.read | ✓ | – | ✓ | existing |
| users.manage | ✓ | – | ✓ | existing |
| users.erase | – | – | ✓ | existing |
| content | – | ✓ | ✓ | existing |
| roles, settings, ai, payments, audit | – | – | ✓ | existing |
| alerts.view (area-scoped) | ✓ (student/email areas) | ✓ (content areas) | ✓ (all) | Phase 2 |
| alerts.manage (acknowledge, resolve, mute) | own areas | own areas | ✓ | Phase 2 |
| ingest.run (start, retry a source) | – | ✓ | ✓ | Phase 7 |
| ingest.schedule (schedules, pause, budgets) | – | – | ✓ | Phase 7 |
| insights (segments, cohorts; aggregates only) | ✓ | – | ✓ | Phase 8 |

The student timeline stays under `users.read`. Saved views are personal and need no permission beyond access to the page they belong to.

## Phase 1 — Admin shell and shared components

**Goal:** one consistent admin frame and component kit, with all 16 existing pages moved into it **without changing what they do**.

**Information architecture**

| Group | Pages (existing pages move here) |
|---|---|
| Monitor | Overview, Alerts (placeholder until Phase 2) |
| Students | Users, Emailed reports, Suggestions and feedback |
| Content and data | Review queue, Error reports, Visa rules, Exchange rates, Flights and health |
| Money | Payments |
| AI | AI usage, Advisor monitor |
| System | Settings, Audit log, System, Diagnostics |

**Role-based home on `/admin`**
- **admin:** the Overview.
- **support:** a support home: the users search, recent sign-ups, emailed reports with delivery problems, and suspended accounts.
- **data_editor:** a data home: review queue counts by type, open error reports, and records nearing staleness.

**Shared components (`components/admin/`)**
- `AdminShell`: a collapsible left sidebar (240 px) with group headings, icons and the current page highlighted. The top bar holds search (a placeholder until Phase 9), the alerts bell (placeholder until Phase 2), an environment badge (Production / Preview) and the staff menu (role, MFA status, sign out). Under 768 px the sidebar becomes a slide-over menu.
- `PageHeader`: title, one-line description, breadcrumbs and primary actions.
- `FilterBar`: wraps the existing date-range filter (today / 7 / 30 / 90 days / custom, in Lagos days), plus filter chips and a reset. The filter state lives in the URL so views can be shared and bookmarked.
- `KpiTile`: value, label, comparison with the previous period (arrow, % change, colour meaning good or bad per metric), and a sparkline slot.
- `DataTable`: server-side sorting, pagination and filtering; column visibility; row selection (used from Phase 3); sticky header; the audited CSV export hooked to the existing export. Under 640 px, rows become cards.
- `DetailDrawer`: a side panel on desktop and a full-screen sheet on phone, with its URL kept in a query parameter.
- `EmptyState`, `ErrorState`, `LoadingSkeleton`.
- `StatusBadge`, `FreshnessBadge` (reusing the student one), `ConfirmDialog` (with a typed-confirmation variant for destructive actions).
- **Admin tokens:** extend the student brand tokens with denser admin spacing, table and chart colours, and alert severity colours. Light and dark mode.

**Data and schema:** none.

**Role and permission impact**
- The sidebar shows only the groups and pages the role can reach, worked out on the server from `permissions.ts`.
- Every page keeps its existing server check. Add one shared `requirePermission()` helper if one doesn't exist, and a test that every route under `app/admin` calls it.

**Tests**

- Vitest: a route-coverage test that fails if any `app/admin/**/page.tsx` or admin API lacks a permission check.
- Playwright (desktop and 360 px): each role sees the right home and groups; a student and an aal1 staff session get 403 or the MFA prompt on every admin route; the mobile menu opens and navigates; each migrated page still renders with its data.

- Each role lands on its own home and sees only its own navigation.
- Every admin page is usable at 360 px without horizontal page scroll; tables switch to cards.

## Phase 2 — Overview, metrics and alerts

**Goal:** the Overview answers "how are we doing" and "what needs me today" at a glance.

**Overview page**
- **KPI tiles** (with change against the previous equal period): visitors, quick searches, deep searches completed, accounts created, emailed reports, report-to-account claims, apply clicks, Plus revenue (NGN), AI cost (USD and NGN), open review items.
- **Funnel chart:** the 7 steps from the brief as horizontal bars, with the count and drop-off % between steps, and the previous period as a faint comparison.
- **Trends:** daily lines for accounts, apply clicks, AI cost and error reports, with the previous period dashed.
- **Needs attention:** a short, ordered list built from open alerts and queues (for example "42 records go stale in 14 days", "Market GBP rate is 16 days old", "3 email bounces today").
- **Breakdowns** (existing, restyled): courses, countries and budgets searched; most saved and most dismissed programmes with reasons.

**Alerts**

| Rule | Default threshold | Area |
|---|---|---|
| Scheduled job failed or didn't run | any missed run | system |
| Email bounce or failure rate | > 5% of the day's sends, or ≥ 10 failures | students/email |
| Review queue backlog | > 50 items, or oldest > 7 days | content |
| Stale records | any ranked record > 110 days since verified | content |
| Market FX rate missing or old | > 14 days | content |
| AI spend spike | today > 2× the 7-day daily average, or above the daily cap in Settings | ai |
| Advisor guard triggers spike | > 3× the 7-day average | ai |
| Error reports from students | ≥ 5 open for more than 3 days | content |
| Payment webhook failures | any | money |
| Ingestion source failing | 3 consecutive failures (active from Phase 7) | content |

- Thresholds are editable in Settings (admin only, audited).
- Lifecycle: open → acknowledged → resolved, or muted until a date. Every change is audited. Rules re-open an alert if the condition comes back.
- **Delivery:** the alerts bell with a count, an `/admin/alerts` page (`DataTable`, filtered by area and severity), and a daily email digest to staff who opt in (Resend).
- **Evaluation:** follows the Phase 0 decision. It runs on Overview load with a short cache, plus the daily digest job, or `pg_cron` if chosen.

**Data and schema**
- `metric_daily` (day in Lagos time, metric key, dimension key, value), filled nightly from `activity_event`, payments, AI usage and email logs; today's values are computed live. Backfill 90 days.
- `admin_alert` (id, rule key, area, severity, status, first seen, last seen, count, context jsonb with no personal data, acknowledged by and at, resolved by and at, muted until).
- `alert_rule_setting` (rule key, threshold jsonb, enabled), or keys in the existing Settings table, whichever matches the code.
- Indexes on `activity_event` (event, occurred_at) if they don't already exist.

**Role and permission impact**
- New permissions: `alerts.view` and `alerts.manage`, scoped by area (see the matrix).
- support sees student/email alerts; data_editor sees content alerts; admin sees all.
- Overview KPIs stay under `overview`; money tiles show only with `payments`, AI tiles only with `ai`.

**Tests**
- Vitest: change-on-previous-period maths, including zero and missing values; Lagos day boundaries around midnight; each alert rule with fixtures that fire and don't fire; re-open behaviour; `metric_daily` aggregation against fixture events.
- Playwright: the Overview renders for admin and support with the right tiles; acknowledging and resolving an alert writes audit rows; a data_editor can't open a money alert; the digest email renders (snapshot) in Resend test mode.

**Acceptance criteria**
- The Overview shows every listed tile with a correct comparison, the funnel with drop-offs, and the trend charts, within 1.5 s on desktop with a warm cache.
- Every alert rule is covered by a test, and seeding a condition makes the alert appear in the bell and on `/admin/alerts`.
- The digest arrives in the Resend test inbox with only the recipient's areas.
- Totals in `metric_daily` match a direct query for the same period.

**Prompt**
> Do Phase 2 of docs/ADMIN_REVAMP_PLAN.md: metric_daily with a 90-day backfill, the new Overview, and the alerts engine with the listed rules, the bell, /admin/alerts and the daily digest (Resend test mode). Use the evaluation approach recorded in docs/ADMIN_DECISIONS.md. Add the alerts permissions to the matrix, audit every alert action, and include tests for every rule. ## Phase 3 — Content hub

**Goal:** one place where data editors see what needs review, what is going stale and where coverage is missing, and can act in bulk safely.

**Pages**
- **Content home** (`/admin/content`): tiles for items awaiting review by type, open error reports, records by freshness band, and coverage gaps; links into each view.
- **Unified review queue** (`/admin/content/review`): one `DataTable` across all record types (programmes, city costs, health plans, and from Phase 4 on, the new Version 1 types).
  - Filters: type, country, province or city, field, level, status, confidence, validation errors, age, assignee, source.
  - Columns: type, title, university or place, confidence, critical fields changed, age, assignee, status.
  - **Detail drawer:** a field-by-field diff against the live record. New values are highlighted. Critical fields (fees, fee year, deadlines, intake dates, English minimums, academic minimum, apply URL, funding amount) are marked. The source page link sits beside the diff, and validation errors appear inline.
  - Actions: approve, edit-then-approve, reject (with a reason), assign to me or to another editor, and re-extract.
  - **Bulk actions:** approve selected (only rows with no validation errors and no critical-field change unless confirmed), reject selected with one reason, assign selected. Each record is approved in its own transaction, so one failure doesn't block the rest, and the result summary lists failures.
  - Keyboard shortcuts on desktop: j/k to move, a to approve, r to reject, e to edit.
- **Freshness** (`/admin/content/freshness`): records by type in bands of 0–60, 60–90, 90–110, 110–120 and >120 days (hidden from students); a list of records going stale in the next 14 days, with "Queue re-verification".
- **Coverage** (`/admin/content/coverage`): a matrix of country × field × level showing live programmes, plus cities missing city costs (using the fallback), provinces or universities without health cover, destinations without flight quotes, and programmes without a funding check (from Phase 4).
- Error reports, visa rules, exchange rates and flights/health move under Content with the shared layout. Behaviour stays the same, and each adds "last verified" and freshness columns.

**Data and schema**
- `review_queue`: add `record_type` (if not present), `assignee_id`, `priority`, `critical_changes` (text array), `rejection_reason`, `reviewed_at`.
- A `content_freshness` view across content tables (type, id, title, last_verified_at, days_old, band) to drive the freshness page and the stale-records alert.
- `reverify_request` (record type, id, requested by, requested at, status), consumed by ingestion (manually until Phase 7).
- Record which fields a reviewer changed (already built per the earlier pilot); show the rate per field on the content home.

**Role and permission impact**
- Everything here needs `content` (data_editor and admin). support has no access.
- Bulk approval of critical-field changes needs an explicit confirmation and is audited per record.

**Tests**
- Vitest: the diff engine (nested fields, arrays such as deadlines and English tests, minor-unit money shown correctly); critical-field detection; bulk approval where some records fail; freshness band edges.
- Database tests: approval transactions, `review_queue` RLS (no student or support access).
- Playwright: filter, open a diff, edit and approve; bulk approve 5 with one invalid row (4 succeed, 1 reported, 6 audit rows); keyboard flow; the freshness list queues a re-verification; phone layout of the queue and drawer.

**Acceptance criteria**
- Every pending record type appears in the one queue, with a correct diff against the live record.
- A bulk action never approves a record with validation errors, and writes one audit row per record.
- The freshness and coverage counts match direct database queries.
- A data_editor can do a full review session on a phone, slower but complete.
- Existing review behaviour, including "programmes before their university" ordering, still holds.

**Prompt**
> Do Phase 3 of docs/ADMIN_REVAMP_PLAN.md: the content home, the unified review queue with diffs, assignment and bulk actions, and the freshness and coverage pages, then move error reports, visa rules, exchange rates and estimates under Content. Keep every approval transactional and audited per record. Commit, push, open a PR and send screenshots.

## Phase 4 — Canada colleges, diplomas and funding (Version 1)

**Goal:** students see Canadian college diplomas and certificates and funded options alongside Master's degrees, and staff can maintain that data through the content hub.

**Points to verify on official IRCC and provincial pages before modelling** (they shape the fields; don't hard-code them):
- Whether non-degree college programmes need a provincial attestation letter, which the master's exemption does not cover.
- Post-graduation work permit eligibility for college programmes: the field-of-study requirement, the minimum programme length, and the exclusion of some public–private partnership colleges.
- Which funding is open to international students. Much provincial and college funding is for residents and permanent residents only. Every funding record must state international eligibility explicitly.

**Data and schema**
- `programme.level`: a new enum, `masters | postgraduate_certificate | graduate_diploma | advanced_diploma | diploma | certificate` (the Ontario credential names are a starting point; map other provinces to it). Existing programmes default to `masters`.
- `institution_type`: `university | public_college | private_college | polytechnic | cegep`, on `university` (or rename the table to `institution` if the code allows it cleanly, with a view for compatibility).
- **College-specific requirement fields:** minimum prior education (secondary school, diploma, degree), English minimums, `pal_required`, `pgwp_eligible` (yes / no / depends on field), `pgwp_field_eligible`, `co_op`, `program_length_months`.
- `funding` (new): name, funder (institution, province or federal), type (scholarship, bursary, tuition waiver, entrance award), `open_to_international` (yes / limited / no), eligible levels, fields, nationalities, minimum grade, amount (minor units and currency, or a percentage of tuition), renewable, deadline, application URL, plus the standard content fields.
- Links: `programme_funding` and `institution_funding` (many to many).
- Extraction: an R3 schema variant for college programme pages and a funding-page schema, each with golden-set pages (5 per type, labelled before any model sees them).

**Matching (student side)**
- Onboarding step 1 or 5: "What do you want to study?": Master's, Postgraduate certificate or diploma, or Either. Default: Either for Canada, Master's for the UK.
- A hard filter on prior education, on `open_to_international` for funding, and on PAL where required.
- A "Funded" chip when an eligible funding record exists, and a "Funding" component in the scoring (scholarship potential, S) that counts only funding the student is eligible for.
- Results group or label by level, so a diploma is never mistaken for a Master's.

**Admin screens**
- Review queue types: `college_programme`, `funding`.
- An institution page listing its programmes by level and its funding.
- A funding page (`DataTable`): filter by province, type, international eligibility and deadline; expiring funding is highlighted.
- Coverage adds level and funded-programme counts by province.

**Role and permission impact:** `content` only. No new permissions.

**Tests**
- Vitest: level filtering, prior-education filter, funding eligibility (international no → never shown), scoring with and without funding, PAL handling.
- Golden-set accuracy for the two new extraction schemas, reported by field.
- Playwright: a student choosing "Either" sees diplomas labelled as diplomas; the Funded chip appears only for eligible funding; an editor approves a college programme and its funding through the hub.

**Acceptance criteria**
- At least 20 reviewed college programmes and 10 reviewed funding records across the chosen provinces, all with official sources.
- No funding record is shown to a student without `open_to_international` = yes or limited, with "limited" clearly labelled.
- Masters-only students see no change in their results.
- New extraction schemas meet the existing critical-field target on their golden sets, or every record goes through human review with that noted.

**Prompt**
> Do Phase 4 of docs/ADMIN_REVAMP_PLAN.md. First verify the PAL, post-graduation work permit and funding-eligibility points on official IRCC and provincial pages and record the sources. Then add programme levels, institution types, college requirement fields, the funding tables, the extraction variants with golden sets, the matching changes and the admin screens. Pilot provinces are in docs/ADMIN_DECISIONS.md. Commit, push, open a PR, and show me the ₦80m worked example with "Either" selected.

## Phase 7 — Ingestion control

**Goal:** staff can see the health of every source and start, retry, pause and schedule runs from the admin, within a spend cap.

**Architecture**
- The admin never runs extraction itself. An admin action inserts a row into `ingest_job`; the Python worker polls for jobs, runs them and writes results.
- Worker hosting follows the Phase 0 decision. If it stays local, "Start run" queues the job and the page shows "Waiting for a worker", with the command to run.

**Data and schema**
- `ingest_source`: URL(s), record type, institution, extraction schema version, schedule (off, weekly, daily in deadline season), active or paused, robots.txt check result, last run and status, consecutive failures.
- `ingest_job`: source(s), requested by, kind (run, retry, re-verify), status (queued, running, done, failed, cancelled), spend cap (USD), started and finished.
- `ingest_run_item`: per page and record: fetched, unchanged, changed → review, invalid, failed (with an error class), tokens and cost, model.

**Admin screens**
- Sources (`DataTable`): health badge, last run, failures, schedule, items waiting for review; bulk pause, resume and run.
- Source detail: run history, item outcomes, diffs sent to review, and a link to the records it produced.
- Jobs: queue and history with cancel and retry.
- Settings additions: a monthly ingestion spend cap and per-job cap, the model per record type (from `/config/ai.json`, read-only here unless already editable in Settings).
- Alert rule activated: a source failing 3 times in a row.

**Role and permission impact**
- New permission `ingest.run` (data_editor and admin): run or retry a source, cancel own jobs.
- New permission `ingest.schedule` (admin): schedules, pause and resume in bulk, spend caps.
- Every job request and schedule change is audited.

**Tests**

## Phase 8 — Students insight

**Goal:** understand who uses StudyBridge, where they drop off and who comes back, without exposing more personal data than each role needs.

**Pages**
- **Segments** (`/admin/students/segments`): build a segment from filters (country of residence, nationality, field, level, budget band, countries chosen, journey stage, consent status, Plus, created date, last active). Shows the count, a breakdown and the journey-stage distribution. With `users.read`, the segment links to the user list; without it, aggregates only.
- **Journey** (`/admin/students/journey`): how many students sit at each stage now and how they moved over the period.
  - Stages: visitor → quick search → deep search complete → results viewed → account or report → saved programme → apply click → Plus.
- **Cohorts** (`/admin/students/cohorts`): weekly cohorts by first account or first deep search, with return activity in weeks 1–8 as a retention grid, and conversion to apply click by cohort.
- **User timeline** (on the user detail page): a chronological view of the user's `activity_event`s, staff actions on them (from `staff_audit`), emails sent and payments, filterable by type.

**Data and schema**
- `student_journey_stage`: a view or nightly table of each user's furthest stage, with dates.
- `metric_daily` dimensions for segments and cohorts, or a cohort table filled nightly.
- Indexes for the user timeline query (actor_id, occurred_at).
- Anonymous visitors appear only in aggregates and only after analytics consent, the same as today.

**Role and permission impact**
- New permission `insights` (support and admin): segments, journey and cohorts as aggregates.
- The user list from a segment and the user timeline need `users.read`. Viewing a timeline writes a `user_viewed` audit row, as viewing a user does today.
- Segment exports with emails need `users.read` and are audited.

**Tests**
- Vitest: stage derivation (including skipped steps such as a report claim without deep search), cohort maths, segment filter building.
- Database tests: no timeline access without `users.read`; RLS on the new tables.
- Playwright: build a segment, open its users, open a timeline (audit row written); support sees cohorts but an aal1 session gets the MFA prompt.

**Acceptance criteria**
- Stage counts add up to the total for the period; cohort grids match direct queries.
- A user's timeline shows events, staff actions, emails and payments in order, with no free text from the advisor.
- Every view of an individual is audited.

## Phase 9 — Search, saved views and polish

**Goal:** make daily admin work fast on desktop and comfortable on a phone.

**Features**
- **Global search** (Ctrl/Cmd K, and the top-bar field): users by email (only with `users.read`), programmes, institutions, funding, review items, alerts and audit entries (only with `audit`). Results are filtered by permission **on the server**. Each user result opened is audited.
- **Saved views:** any `DataTable` can save its filters, sort and columns as a personal view, set one as default, and share it with other staff of the same role (read-only for them).
- **Notification preferences:** per staff member, which alert areas and severities go to the digest; optionally an immediate email for critical alerts (rate-limited).
- **Phone polish:** review a full day's tasks on a 360 px phone (alerts, review queue, error reports, user lookup) and fix anything awkward; larger tap targets in tables-as-cards.
- **Performance:** every admin page under 1.5 s on desktop with a warm cache; heavy charts load on demand.
- **Accessibility:** keyboard navigation through the shell, tables and drawers; WCAG 2.2 AA contrast in both themes.

**Data and schema**
- `staff_saved_view` (owner, page key, name, state jsonb, shared with role, is default).
- `staff_notification_pref` (staff, area, severity, channel).
- Search uses existing tables with indexes (trigram on names and emails) or Postgres full-text search.

**Role and permission impact:** none new; search and shared views respect existing permissions.

**Tests**
- Vitest: search permission filtering (support never sees audit results; data_editor never sees users).
- Playwright: Ctrl K finds a programme and opens it; save, share and load a view; notification preferences change the digest contents; a full phone run-through.

**Acceptance criteria**
- A search never returns a record the staff member couldn't open directly.
- Saved views restore exactly the saved table state.
- The phone run-through is completed without horizontal page scroll or blocked actions.
- Performance and accessibility targets met, measured and recorded in `docs/ADMIN_DECISIONS.md`.
